# Benchmark — the review side, with the plugin and without

`docs/TEST-CASES.md` defines `E2E-02` as "give the same receipts to a plain session,
then run the plugin, and score both". This directory is that comparison, instrumented
and repeatable: token usage, cost, wall time, subagent invocation and per-line accuracy,
over three sequential submissions, three runs per arm.

Finance side only. Every trip ships a finished `submission.csv`, as if the employee had
already sent it, so `/expense-submit` is not part of the measurement.

## Run it

```bash
bash bench/run.sh --dry-run        # print every command, spend nothing
bash bench/run.sh                  # all arms, 3 runs each, policy A
python3 bench/measure.py           # transcripts -> metrics.json
python3 bench/score.py             # outputs + ground truth -> scores.json
python3 bench/report.py            # -> bench/REPORT.html
```

Useful flags: `--arm skill`, `--runs 1`, `--policy b`, `--model opus`, `--effort high`.
Budget is capped per run by `--max-budget-usd` (default $2.00, `BENCH_BUDGET` to change).
A full policy-A matrix is ten sessions and costs a few dollars.

`run.sh` moves an existing `~/.expense-claim-review` aside before the skill arm and
restores it on exit, so your own policy store survives a benchmark run.

## The arms

| Arm | Plugin | Policy | Prior claims |
| --- | --- | --- | --- |
| `base-strict` | none | pasted into the prompt | none |
| `base-fair` | none | pasted into the prompt | pasted in |
| `skill` | `--plugin-dir .` | `/setup-expense-policy`, once | `claims.csv`, carried forward |
| `skill-noagents` | `--plugin-dir .` | same | same, with `--disallowedTools Agent` |

Both baselines are given the output schemas in full (`prompts/template.md`), so a
format failure is a failure to follow instructions, not a failure to guess them.

### Controls

- **No shared context.** Fresh `--session-id` and a fresh working directory per run;
  nothing is resumed or continued.
- **No plugin leakage into the baseline.** Baseline arms run under `--safe-mode
  --strict-mcp-config`. Without it the repo's own `CLAUDE.md` would describe the
  plugin to the arm that is supposed to know nothing about it.
- **Equal tools.** Both arms get the same `--allowedTools`. An early smoke run had
  the baseline denied a Bash call while the skill arm was not, which would have
  biased the token and time numbers.
- **Same working directory contents.** The only differences between arms are the
  plugin, where the policy comes from, and whether a ledger exists.

### Known asymmetry

The skill arm reads `policy-a.docx` directly; a headless baseline cannot be handed an
attachment, so it receives the `pandoc` text extraction of the same file. Same content,
different channel. The report states this rather than hiding it.

## The two policies

**Policy A — `policies/policy-a.docx`**, the Workable sample template, verbatim.
It contains **no digits at all**: no meal cap, no approval threshold, no alcohol rule,
no FX rule, no duplicate rule. Its quantities are unfilled placeholders (`[three
months]`, `[one month]`). That makes it a direct test of the plugin's central
invariant — *policy silent → `UNSPECIFIED`, ask, never default* — because any number a
reviewer measures against was invented.

**Policy B — `policies/policy-b.md`**, the same document with every placeholder filled
in and the silences closed. Tests the opposite failure: applying rules that do exist,
with the arithmetic shown.

## The datasets

Three sequential trips for one traveller, generated by `datasets.gen.py`, which also
emits the ground truth so a receipt and the amount it is scored against cannot drift
apart. Edit the generator, never the fixtures.

| Probe | Where | What a correct reviewer does |
| --- | --- | --- |
| Named non-reimbursables | all three trips | reject, citing the clause |
| Meal-cap silence | `T1-03`, `T2-04`, `T3-03` | A: route for approval, quote no number. B: apply the cap, show the arithmetic |
| Alcohol silence | `T1-04` | A: **not** non-reimbursable — the word never appears in the policy. B: excluded |
| Filing deadline | `T2-06` | out of window, 163 days after the expense |
| Duplicate | `T2-01`, `T3-01` | matches a row already in the ledger |
| Tamper | `T2-03` | submission says 8,400, receipt says 6,400 — the receipt wins, both recorded |
| Illegible total | `T2-08` | `MISSING-DATA`. Any number here is fabricated |
| Foreign currency | `T3-07` | A: flag and ask for a rate. B: convert at the specified rate |

The duplicate and tamper probes are in trips 2 and 3 deliberately. Run 1 is close to
parity between arms; the gap is designed to open as the ledger fills. `T3-01` keys on
the **corrected** 6,400 from `T2-03`, so it is only catchable by a reviewer that caught
the tamper first.

**Receipt filenames name the merchant and nothing else.** An early run had a baseline
catch the duplicate purely from the string `resubmit` in a filename — the fixture was
answering its own question. Never encode a verdict in a name.

## How scoring works

Verdicts are read from `claims.csv` and `exceptions-queue.csv` first, then from the
report as a fallback, because a settled `NON-REIMBURSABLE` line belongs in neither CSV.
Free text is mapped onto the verdict vocabulary through `score.py`'s `SYNONYMS` — a
baseline has never read `skills/expense-review/SKILL.md` and writes "rejected", not
`NON-REIMBURSABLE`, so comparing raw strings would measure vocabulary rather than
judgement.

A line's `claimable: null` in the ground truth means the policy genuinely does not
determine the amount; the line is then scored on its verdict and its `must_not`
assertions only. Under Policy A a lot is legitimately undecidable, and saying so is
the correct answer.

The invariant checks (`INV-CAP`, `INV-ALC`, `INV-AMT`, `INV-FX`) are where a wrong
answer is worse than no answer. `INV-CAP` is a heuristic — it looks for a sentence
asserting a cap or limit with a number that is not one of the receipt amounts — so it
keeps the offending sentence as evidence for a human to confirm.

## Measurement notes

`measure.py` reads two independent sources: each run's terminal `result` event (cost,
turns, duration — Claude Code's own totals) and the session JSONL. Three things it
exists to get right, all of which silently corrupt a naive count:

1. **Assistant usage rows repeat per content block.** Group by `message.id` and keep
   the highest `apiBlockIndex`. Summing raw double-counts input; taking the first
   block can undercount output by orders of magnitude.
2. **Subagent tokens live in separate files**, under
   `~/.claude/projects/<slug>/<session-id>/subagents/`. A parent transcript alone
   omits every delegated call — exactly the work the skill arm does.
3. **The tool is named `Agent`, not `Task`.** Counting `"name":"Task"` returns zero.

Agent invocation is evidenced twice over: `Agent` tool-use blocks in the transcript,
and the plugin's own `PreToolUse` hook writing `agent-invocations.log` next to
`audit-log.txt`. The two should agree; `report.py` prints both.
